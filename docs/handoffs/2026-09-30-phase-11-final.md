- typing in the editor
- pasting an image

React 19 `<script>` rejection in Phase 2 and the `TabsContent`-outside-`Tabs`

erroring" as a weak signal.

## Known limitations carried forward

- **No cross-device sync, no public share links.** Both need the backend phase.
- **Evernote import is lossy** for markup outside the handled tag set, and the
  UI says so.
- **Attachments are images only.**
- **Browser storage is still evictable.** Everything in the app surfaces this,
  and the README leads with it, but the mitigation is a habit, not a mechanism.
- `usePwa.tsx` service-worker registration only runs in production, so it has
  never actually cached anything until it is served over HTTPS.

## Rename: Notes -> Sidenote

Display name `Sidenote`, identifiers `sidenote`.

**What changed (app identity):**
- `package.json` name, page title + `applicationName`, manifest `name`/`short_name`
- `DB_NAME` — the IndexedDB database is now `sidenote`, not `notes`
- `THEME_STORAGE_KEY` — `sidenote:theme`
- service-worker cache names
- the backup manifest's `app` field and the default archive filename
  (`sidenote-backup-<stamp>.zip`)

**What deliberately did NOT change (domain vocabulary):** the `notes` table,
the `notes/` folder inside a backup, the `notes` query key, the `"notes"` pane
id, `seed-notebook-*` ids, and the "Notes" heading over the note list. Those
mean *note documents*, not the app. Renaming them would be a rename of the
domain, not the product.

**Consequence:** an existing browser profile's data is orphaned, not migrated.
The old `notes` database and `notes:theme` key are left behind untouched. That
is acceptable because nothing has shipped and there is no real user data yet —
but if that changes, the old database needs a migration rather than a rename.
